# nfcraft — product brief

## Purpose

Turn a box of physical NTAG215 cards into durable, useful, well-managed touchpoints without turning the owner into a full-time production operator. The first experience is a personal contact card. The product is the **workstation plus trustworthy card lifecycle**, not a generic NFC demo or an AI chatbot with a write button.

Product phrase: **Prepare. Tap. Verify. Keep improving.**

## Three people, three interfaces

The owner prepares a profile/batch, gives bounded approval, presents/removes cards, and resolves exceptions. Their AI agent drafts content, prepares batches, diagnoses failures, exports data and improves the software. A card recipient sees only a fast public page and explicit actions such as saving a contact or opening a project. Recipients never see the operator app, internal UID, reader controls or private agent tools.

## Primary workflow

Select or create a profile -> create a batch and confirm its durable origin -> approve a limited run -> place one card -> inspect -> reserve identity -> write -> verify -> remove -> next card -> publish reviewed routes -> independently test the encoded URL, phone and printed QR -> issue cards.

An interruption stops the run. The original identity remains associated with that card. A recovery operation is explicit, not a new-card allocation. Updating public content does not require changing issued card URLs.

## Successful product behavior

A novice can distinguish demo, read-only hardware and write-enabled hardware immediately. They do not need to click Write on every card. They receive clear placement/removal/error guidance. The system never shows a green ready-to-distribute badge merely because a transport call returned success. It remains useful offline for local preparation while clearly explaining that an unpublished URL is not usable by visitors.

The workbench is calm and intentional: warm neutral surfaces, restrained green/ink contrast, clean type, large next-action area, minimal ornament. Speed means fewer avoidable steps and good recovery, not unmeasured RF claims. A physical one-card positioning tray can help operations, but no feeder is required or implemented.

## First release boundary

Reliable local browser app and agent interface, one tested hardware path, ten-card pilot, a usable public profile/vCard, repeatable startup and publication, backups and honest status. Do not block this on a new desktop framework, Android companion, public AI assistant, fleet cloud, analytics dashboard or custom robotic hardware.

## Later value, in order of need

Publication diff/receipt and ready-to-issue tracking; inventory search and quarantine queue; multiple profiles/campaign presets; labels/QR print sheets and human-readable physical IDs; repeatable desktop distribution; additional readers; a paired Android station with an honest capability model. Multiple workstations need namespaces, idempotency, conflicts and authority rules before sharing a public database.

Open-ended NFC formats, login/access-control use, payments, anti-counterfeiting claims and arbitrary memory management are outside this product's current scope. Public route identifiers are not security credentials.

## Metrics to collect, not invent

Count first-pass verified cards, quarantined cards, successful original-ID recoveries, human placement/removal time, measured hardware cycle time, publication failures, and final phone/print QA failures. Separate simulated timings from physical measurements. Do not identify visitors or store IP/contact information by default just to make a dashboard look active.

## Longevity

An issued card is a commitment to keep its URL usable. Prefer an owner-controlled hostname, preserve route mappings and namespace strategy, and make profile updates reversible. Software upgrades must not reset inventory, silently migrate old data, or retire issued identities.
